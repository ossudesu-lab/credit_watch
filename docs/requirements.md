# 要件メモ（2026-09-23）

仮の名前: credit_watch

## 目的

Anthropic API のクレジットを**何にどれくらい使っているか**を見えるようにし、
使いすぎを**早めにスマホへ知らせる**。

## 背景

2026-08-19、kaigo_matching の eval を1日約530回まわして残高が尽き、
公開中のアプリが 502 になった。eval と本番が同じアカウントの残高を使っていたため。

## やること / やらないこと

| やる | やらない |
| --- | --- |
| プロジェクト別・用途別（本番 / eval）の使用量の記録と集計 | 使いすぎたときに止める（Console のワークスペース上限で設定済み） |
| しきい値を超えたときの通知（まずメール、後で LINE） | 他人の API キーを預かる |
| Console の使用量ページとの照合（記録漏れの検出） | Admin API の利用（個人アカウントでは使えず、組織化は戻せない可能性があるため見送り） |

## 利用者

自分ひとり。見るのは主にスマホ（通知）、ときどき PC（集計）。

## データの取り方

各プロジェクトが、API の応答に入っているトークン数（`usage`）を1回ごとに記録する。
記録するのは**数字だけ**（日時・プロジェクト・用途・モデル・入力/出力トークン数）。

既に仕込みどころがある:

- kaigo_matching … `api/_lib/anthropic.js` の `callAnthropic` に `onUsage` フックあり（今は eval だけが使っている）
- kaigo_mcp … `kaigo_mcp/agent/backends.py` で `usage` を取得済み

## セキュリティ

- **プロンプト本文・応答本文は記録しない。** kaigo_matching は介護記録を扱うため、記録の中身が漏れると PII 事故になる
- API キーは記録にもログにも出さない
- 公開リポジトリの GitHub Actions のログは誰でも読める。生のレスポンスを出力しない

## 照合

Console の使用量ページは API キー別に絞り込める。
週1回、自分の記録の合計と Console の数字を比べ、ずれが一定以上なら「記録漏れの疑い」として扱う。

## 通知の条件（2026-09-23 決定）

前提: 入金は $5 で、ワークスペース上限も $5。少額で固定しているので「いつもより○円増えたら」は使わない。
普段よく使う人には通知が多すぎてうるさくなるため。

| 種類 | 条件（仮） | 目的 |
| --- | --- | --- |
| 急増 | 1日の使用額が $1（上限の20%）を超えた | 8/19 の事故の型（1日で使い切る）を早めに止める |
| 残り少 | 残りが $1 を切った | 入金の判断をする |
| 定期レポート | 毎週末に1通 | 何にどれくらい使ったかの内訳 |

- 同じ理由の通知は1日1回まで（しつこくしない）
- 残高を返す API はないので、**入金額（手入力）−記録の合計**で出す。照合のときに Console の数字で補正する
- 数値は仮。実際に使ってみて調整する

## 記録の置き場所（2026-09-23 A に決定）

kaigo_matching の本番は Vercel のサーバーレス関数で、ファイルに書き残せない。

| 案 | 中身 | 良い点 | 弱い点 |
| --- | --- | --- | --- |
| **A. 外部の小さなDB（Upstash Redis）** | 各プロジェクトが「日付×プロジェクト×用途×モデル」の数字を足し込む | 本番もevalも同じ場所。無料枠（月50万コマンド）で十分 | サービスが1つ増える。本番の処理に書き込みが1つ加わる |
| B. Vercel のログに書いて後で拾う | 本番は `console.log` で1行出すだけ | 本番のコード変更が最小 | Hobby はログを1時間しか残さない。拾い損ねると消える。eval側は別の仕組みが要る |
| C. 受け口のAPIを作り、その裏にDB | 各プロジェクトは credit_watch のURLに送るだけ | プロジェクト側がDBの鍵を持たない | 認証まで作る必要があり、一番重い |

A を採る場合の約束:

- **記録に失敗しても本番は落とさない。** 書き込みは待たずに投げ、失敗は握りつぶして本番の応答を優先する
  （ただし Vercel は応答を返すと処理が打ち切られることがあるため、書き込みを最後まで走らせる仕組みを使う）
- 記録の数字の正は Console。記録が抜けても照合で気づける

## 金額の計算（2026-09-23 決定）

- **内部はドルで持つ。** 入金も上限もドルなので、判定もドルで行う。円は表示だけで、レートは設定ファイルの固定値（手で更新）。
  為替APIは使わない（壊れる箇所が増えるうえ、この用途では1円単位の精度は要らない）
- 単価表は credit_watch に**1つだけ**置き、確認日と出典URLを添える。トークンは4種類（入力・出力・キャッシュ書き込み・キャッシュ読み込み）で計算する
- **単価表にないモデルは0円にしない。**「単価不明」として通知とレポートに出す

作る前に見つかった実例（2026-09-23 時点）:

- kaigo_matching の `scripts/eval-usage.js` と kaigo_mcp の `agent/usage.py` は、Sonnet 5 を $3/$15 で計算している。
  実際は $2/$10（予定されていた値上げが中止になった）。**単価表は放っておくと古くなる**
- 本番の連絡文で使う `claude-sonnet-4-6` は、どちらの単価表にも入っていない

## 実行の場所と間隔（2026-09-23 決定）

- 公開リポジトリの GitHub Actions で**1時間おき**。記録は各プロジェクトがその場で書くので、確認の遅れは最大1時間
- GitHub Actions の定時実行は数分〜十数分遅れることがある。この用途なら問題ない
- 公開リポジトリで**60日間動きがないと、定時実行は自動で止まる**。止まっても気づけるよう、
  **週末のレポートを生存確認も兼ねる**ことにする（「週報が来なかったら壊れている」）
