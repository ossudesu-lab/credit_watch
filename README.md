# credit_watch

Anthropic API のクレジットを**何にどれくらい使っているか**を集計し、
使いすぎを**早めにメールで知らせる**仕組み。自分の個人開発3本を対象に運用している。

> ステータス: **運用中（2026-09-24〜）。**
> 本番（kaigo_matching）と eval（kaigo_matching・kaigo_mcp）の使用量を記録し、1時間おきに見張っている。

## なぜ作ったか

2026-08-19、[kaigo_matching](https://github.com/ossudesu-lab/kaigo_matching) の eval を1日に約530回まわして
API の残高を使い切り、**公開中のアプリが502で止まった。**
eval と本番が同じアカウントの残高を使っていたため。

使いすぎを「止める」ことは、Console のワークスペース上限で既にできている。
足りなかったのは、**何が残高を食っているかが見えないこと**と、**尽きる前に気づけないこと**だった。

## 何をするものか

```
[kaigo_matching 本番 (Vercel)] ─┐
[kaigo_matching eval (CI)]     ─┼─ 記録係 ──トークン数を足し込む──▶ [Upstash Redis]
[kaigo_mcp eval (ローカル)]     ─┘                                     │
                                                                       ▼ 1時間おき
                                                    [見張り番 (GitHub Actions)]
                                                                       │
                                                                       ▼ 条件に当たったら
                                                                   [メール]
```

- **記録係**（`recorder/`）… 各プロジェクトに入れる数十行の部品。Claude を呼ぶたびに、返ってきたトークン数を足し込む
- **見張り番**（`watcher/`）… 記録を金額にして、次の条件で通知する

| 通知 | 条件 | 狙い |
| --- | --- | --- |
| 急増 | 1日の使用額が $1（上限の2割）を超えた | 8/19 の型（1日で使い切る）を途中で止める |
| 残り少 | 残りが $1 を切った | 入金するか考える |
| 異常 | 単価の分からないモデル・読めない記録がある | 金額が実際より少なく出ている恐れを知らせる |
| 週報 | 毎週日曜20時 | 本番 / eval ・モデル別の内訳。**生存確認を兼ねる** |

同じ理由の通知は1日1回まで。

## やらないこと

- **止めない。** Console のワークスペース上限に任せる
- **他人の API キーを預からない**
- **公式の Usage & Cost API（Admin API）を使わない。** 個人アカウントでは使えず、
  組織への切り替えは戻せない可能性があった。本番が動いているアカウントで試す操作ではないと判断した

## 設計で気をつけたこと

**記録するのは数字とラベルだけ。** kaigo_matching は介護記録を扱う。
記録係はプロンプトも応答も送らない。Redis に入るのは `kaigo_matching|prod|claude-haiku-4-5|in` → `1596` のような形だけ。

**記録係は本番を絶対に落とさない。** 例外は外に出さず、1.5秒で打ち切る。
Vercel では `waitUntil` で応答の後ろに回し、応答を待たせない。
監視のための部品が本番を壊したら本末転倒なので、偽の記録先を固まらせても本番の応答が遅れないことを確かめた。

**「失敗のログが無い」を成功とみなさない。** 設定が無いとき記録係は黙って何もしないので、
ログが空なのは成功とも設定漏れとも読める。本番に入れたときは Upstash の中身を直接見て確かめた。

**単価表に無いモデルを0円にしない。** 金額に入れず「単価不明」として通知する。
作る前に既存2作品の単価表を最新の料金と突き合わせたら、本番で使っているモデルが表に入っていなかった。
単価表は放っておくと古くなる。

**公開ログに金額も鍵も出さない。** このリポジトリは公開で、Actions のログは誰でも読める。
見張り番は「通知 1 件」とだけ出す。失敗したときも、例外の文面は出さずに種類と安全な手がかりだけを出す。

**見張り番が止まったことにも気づけるようにする。** 公開リポジトリは60日動きがないと定時実行が止まる。
週報は使用額が0でも送るので、「週報が来なければ壊れている」と分かる。
Upstash が読めないときは失敗で終わらせ、GitHub の失敗通知で気づけるようにしている。

## 運用で起きたこと

**初回の見張りが `URLError` で落ちた。** GitHub の Secrets に、接続先URLを引用符ごと貼っていた
（`.env` 形式の表示をそのままコピーしたため）。
公開ログには中身を出さない設計だったので、ログからは原因が分からなかった。
そこで、値そのものは出さずに**よくある入れ間違いを言い当てる**ようにした
（前後の空白・引用符、`redis://` 形式の値の取り違え、`https://` の抜け、変数の名前の抜け）。

## 使い方

### テスト

外部サービスは使わない。判定は手で書いた数字を渡して確かめる。

```bash
python -m unittest discover -s tests -t .
```

```bash
npm test
```

Python 43件・JS 10件。記録係は JS 版と Python 版があり、
両方が同じコマンドを作ることを共通の答え（`recorder/cases.json`）で確かめている。

### 記録係を入れる

`recorder/recorder.js` か `recorder/recorder.py` を対象のプロジェクトにコピーし、
Claude の応答を受け取った直後に `recordUsage(model, usage)` / `record_usage(model, usage)` を呼ぶ。
パッケージにしていないのは、1ファイル数十行で依存も無いため。

環境変数が1つでも無ければ何もしない。

| 名前 | 中身 |
| --- | --- |
| `KV_REST_API_URL` / `KV_REST_API_TOKEN` | Upstash の接続先と鍵（Vercel の Upstash 連携が付ける名前に合わせた） |
| `CW_PROJECT` | プロジェクト名 |
| `CW_PURPOSE` | `prod` か `eval`。呼ばれ方から推測せず、ここで決める |

### 見張り番

GitHub の Secrets / Variables に置く。**値に引用符を付けないこと。**

| 名前 | 種類 | 中身 |
| --- | --- | --- |
| `KV_REST_API_URL` / `KV_REST_API_TOKEN` | Secret | Upstash の接続先と鍵 |
| `CW_SMTP_USER` / `CW_SMTP_PASS` | Secret | Gmail のアドレスとアプリパスワード |
| `CW_MAIL_TO` | Secret（任意） | 送り先。無ければ送信元に送る |
| `CW_DEPOSIT_USD` / `CW_DEPOSIT_DATE` | Variable | 入金額と入金日。残高 = 入金額 − 入金日以降の使用額 |
| `CW_USD_JPY` | Variable | 表示用の固定レート |

手元で試すときは `python -m watcher.main --dry-run`（送らずに画面に出す。印も付けない）。

## 分かっている限界

- **残高は推定。** 残高を返す API が無いので、入金額から記録の合計を引いている。
  記録係を入れていない呼び出し（Console の Playground など）は数えられない。週報を見て Console の数字と手で照合する
- **eval が異常終了すると、最後の1回ぶんの記録が抜けることがある**（kaigo_matching の eval が `process.exit` するため。1円未満）
- **単価表は手で更新する。** 表に無いモデルは「単価不明」で気づけるが、既にあるモデルの値上げには気づけない
- **通知はメールだけ。** LINE は必要になったら足す

## 構成

```
recorder/   記録係（JS版・Python版と、両者の共通の答え）
watcher/    見張り番（金額計算・判定・Upstash・メール）
tests/      Python のテスト
docs/       要件メモと設計メモ
.github/    見張り番（毎時）とテストのワークフロー
```

詳しい判断の経緯は [docs/requirements.md](docs/requirements.md) と [docs/design.md](docs/design.md)。
